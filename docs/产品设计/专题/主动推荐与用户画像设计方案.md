# 主动推荐与用户画像设计方案

- **状态**：2026-11-25 评审通过，第一期已实现（`src-tauri/src/radar/`、`src-tauri/src/scholar.rs`、`src/workspaces/literature/Recommendations.tsx`）。已定：在本机运行；论文、新闻、博客都推；画像分账号和项目两层，推荐以项目为主；模型费用走用户的官方模型额度或用户自己的密钥；内测期间不分免费版和专业版；第一期覆盖 AI 和计算机；第十六节其余事项按建议执行。
- **第一期和设计的出入**：信源只有 arXiv 和 OpenAlex（关系召回、RSS 等在后续几期）；入口是文献侧栏工具栏里的“推荐”按钮（现在的侧栏已没有“订阅”切换）；“个性化推荐”开关和“清除推荐数据”放在 设置 → 数据与备份；每个项目每天的预算是 5 万 token，按服务商报的用量计（推理模型完整跑一轮约 2.7 万）；代码按流程分文件（`library`、`profile`、`sources`、`recall`、`judge`、`brief`、`store`），后台调度在 `worker.rs`，前端命令在 `commands.rs`（`radar_visit`、`radar_view`、`radar_feedback`、`radar_save`、`radar_clear`），arXiv 和 OpenAlex 的代码移到 `src-tauri/src/scholar.rs`，和 AI 助手共用。
- **范围**：用户画像（账号层）、研究画像（项目层）、信息源、搜推引擎、主动发布、界面、调度与计费、AI 助手的上下文、数据存储、代码结构、分期。
- **入口**：文献 → 订阅 → 推荐（现在是占位标签），通知中心推送每日简报。
- **参考的开源项目**：
  - [Memobase](https://github.com/memodb-io/memobase)（Apache-2.0）：用户画像按“主题 / 子项”组织，加事件时间线，信号攒一批再合并，省 token。借鉴结构和合并流程，用 Rust 重写，不依赖它的服务端。
  - [AIHOT](https://github.com/KKKKhazix/AIHOT)（MIT）：信源分级、宽进的预筛、同一标准独立打两次分、同一事件聚类、按独立信源算热度、按规则编排日报。借鉴流程，改写提示词，注明出处。
  - [zotero-arxiv-daily](https://github.com/TideDra/zotero-arxiv-daily)（AGPL-3.0）：把文献库当兴趣画像，新论文按与文献库的相似度打分，越新加入的论文权重越高。**只借鉴思路，不用代码**（许可证与 Capsio 的 Apache-2.0 不兼容）。

## 一、目标与原则

**目标**：用户什么都不用设置。项目里有几篇论文之后，Capsio 每天推荐和这个项目相关的新论文、新闻和博客，每条说清楚为什么推给他。

| 原则 | 具体做法 |
| --- | --- |
| **无感** | 画像和推荐都在后台自动做。没有“画像”页面，不让用户填问卷、选标签。用户只看到推荐结果和推荐理由 |
| **能关、能清除** | 设置里有一个“个性化推荐”开关（默认开）和“清除推荐数据”。这是用户唯一需要知道的设置，也满足算法推荐必须能关闭的规定 |
| **本机运行、本机存储** | 画像、候选内容、反馈都只在用户电脑上。调用模型时，只把当次需要的片段发给用户选的模型；服务器不存画像 |
| **费用走用户** | 官方模型扣用户额度；用户自己的密钥不经过我们，也不扣额度 |
| **省 token** | 能用规则和本地算法的不用模型；模型只做“理解和判断”；同一条内容只处理一次 |
| **不打扰** | 推荐只进“推荐”页和通知中心，不弹窗，不自动开标签，不打断正在编辑的内容 |
| **以项目为主** | 每个项目一份推荐。账号层画像只补充（关注的作者、不想看的主题、语言偏好），不单独成一份推荐 |

## 二、模块划分

| 模块 | 做什么 | 输入 | 输出 | 用户能看到吗 |
| --- | --- | --- | --- | --- |
| **1. 信号采集** | 记录能反映兴趣的行为和内容 | 文献库、阅读、笔记、文档、稿件、AI 对话的提问、推荐反馈 | 本机信号流 | 否 |
| **2. 用户画像** | 跨项目的“这个人是谁、关注什么、不想看什么” | 信号流 | 账号层画像 | 否 |
| **3. 研究画像** | 每个项目在研究什么 | 项目的论文、笔记、稿件、反馈 | 项目层画像（主题、关键词、检索式、种子论文） | 否 |
| **4. 信息源** | 从外部抓取新内容，统一成一种格式 | 研究画像给的分类和检索式、内置信源目录 | 候选内容库 | 否 |
| **5. 搜推引擎** | 召回、去重、打分、聚类、排序 | 候选内容、两层画像 | 每个项目的推荐列表和推荐理由 | 只看到结果 |
| **6. 主动发布** | 定时生成简报，挑出要立刻提醒的 | 推荐列表 | 每日简报、即时提醒 | 是 |
| **7. 反馈** | 把用户的操作变成画像的调整 | 加入文献库、稍后读、不感兴趣、点开、阅读时长 | 信号流 | 只看到按钮 |
| **8. 调度与计费** | 什么时候跑、用哪个模型、花多少 | 应用状态、模型设置、额度 | 后台任务 | 否 |
| **9. 界面** | 推荐页、通知中心、设置开关 | 简报和推荐列表 | — | 是 |

模块 4 信息源单独隔离：它只负责“抓什么、从哪抓、抓下来是什么格式”，不知道用户是谁。画像通过“检索请求”告诉它要什么，所以换信源、加信源都不影响其他模块。

## 三、信号采集

| 信号 | 从哪来 | 用来做什么 | 权重 |
| --- | --- | --- | --- |
| 文献库论文 | 论文记录（Zotero / BibTeX / RIS 导入的标题、作者、年份、期刊、摘要、DOI、关键词）；没有记录的 PDF，用应用已有的 PDF.js 读取通道读前两页，取标题和摘要 | 研究画像的主要依据，也是相似度召回的“兴趣库” | 最高；最近加入的权重更高（按加入时间衰减） |
| 阅读行为 | 打开论文、阅读时长、高亮、批注、翻译 | 区分“收藏了”和“真在读” | 高 |
| 笔记和项目文档 | 标题和前几段 | 补充研究画像的主题和用词 | 中 |
| 写作稿件 | `\title`、`\begin{abstract}`、模板（如 ICLR 模板说明目标会议） | 研究画像的方向；用户画像的投稿目标 | 中 |
| AI 对话 | 只取用户的提问，不取 AI 的回答 | 用户画像（关注点、方法、身份阶段） | 中 |
| 推荐反馈 | 第八节 | 调整两层画像的权重和排除项 | 高 |

- **存放**：本机的信号表（第十二节），每条记下类型、项目、内容摘要（截断）、时间。
- **整理**：攒一批再交给模型提炼（参考 Memobase 的缓冲），每天最多一次，不在每次操作时调模型。
- **不采集**：论文全文、AI 的回答、代码内容、其他成员的阅读行为。

## 四、用户画像（账号层）

结构参考 Memobase：画像由固定的主题和子项组成，每个子项是一条带证据的事实。

| 主题 | 子项 | 例子 |
| --- | --- | --- |
| 基本 | 身份阶段、学科大类、机构类型 | 博士生；计算机；高校 |
| 研究 | 长期方向（跨项目）、常用方法、常用工具 | 大模型智能体；强化学习；PyTorch |
| 阅读偏好 | 语言、内容类型（论文 / 综述 / 新闻 / 博客 / 代码）、常读时段 | 中英都读；偏好论文和代码 |
| 关注 | 作者、机构、会议和期刊 | 某实验室；ICLR、NeurIPS |
| 投稿 | 目标会议和截稿时间 | ICLR 2027 |
| 不想看 | 主题、来源 | 加密货币；某营销号 |

- **每个子项记**：内容、置信度、证据条数、最后更新时间、来源（推断 / 用户操作）。
- **怎么更新**：每天第一次空闲时，把新信号和现有画像一起交给模型，要求只输出改动（新增、修改、删除）的 JSON。只有证据支持的才写；同一子项最多保留若干条（参考 Memobase 的 `max_profile_subtopics`）；长期没有新证据的降低置信度，最后删掉。
- **“不想看”优先**：用户点“不感兴趣”时直接写入，不等每天的批量。
- **存放**：只在本机。同一账号的其他设备各自建（项目和论文本来就同步，结果基本一致），第一期不上传、不同步。
- **用途**：给搜推引擎补充关注和排除；压缩成一段摘要给 AI 助手（第十一节）。

## 五、研究画像（项目层）

| 字段 | 内容 |
| --- | --- |
| 主题 | 3–8 个，每个有名称、一句话描述、中英关键词、代表论文（文献库里的论文 id）、权重 |
| 分类 | arXiv 分类（如 cs.CL、cs.AI）、OpenAlex 的 topic 编号 |
| 检索式 | 每个主题 2–3 条，分别给 arXiv、OpenAlex 和联网搜索用 |
| 种子论文 | 文献库里有 DOI 或 arXiv 号的论文，用来找“引用了它的新工作”和“作者的新作” |
| 排除 | 这个项目不要的主题和来源（来自反馈） |

- **什么时候建**：项目文献库有 3 篇以上论文时，取最近加入和读得最多的至多 40 篇的标题和摘要，加上项目名、稿件标题，交给模型输出上表的 JSON。
- **什么时候更新**：新增 3 篇以上论文，或距上次一周；反馈只调权重和排除项，不调模型。
- **不展示给用户**。推荐理由里提到的是具体论文（“和你文献库里的《X》方法相近”），不是画像本身。

## 六、信息源（采集层）

所有信源输出同一种格式：标题、链接、作者、发布时间、摘要、语言、类型（论文 / 新闻 / 博客 / 代码）、DOI 或 arXiv 号、信源、信源等级。

**信源类型**（参考 AIHOT 的六类，去掉需要付费接口的 X 和公众号）：

| 类型 | 做法 | 用于 | 分期 |
| --- | --- | --- | --- |
| arXiv | 按研究画像的分类取每日新文（arXiv 美东 20:00 公布，约北京时间次日早上），再按检索式补搜 | 论文 | 第一期 |
| OpenAlex | 免费接口：按 topic 和检索式取近 7 天的新作；`cites:` 种子论文；关注作者的新作 | 论文 | 第一期 |
| RSS / Atom | 期刊目录、实验室和公司博客、科技媒体 | 论文、博客、新闻 | 第二期 |
| 网页列表 | 没有 RSS 的网站，用 CSS 选择器取列表 | 新闻、博客 | 第二期 |
| 联网搜索 | 复用 AI 已有的网页搜索，按主题搜近一天的新闻 | 新闻 | 第二期 |
| GitHub | 和主题相关的仓库的新版本和热门仓库 | 代码 | 第三期 |

- **内置信源目录**：按学科分组，每个信源标等级（参考 AIHOT：T1 官方一手、T1.5 准官方、T2 媒体和个人）和用途（进推荐 / 只算热度）。按研究画像的学科和分类自动选用，用户不用配置。第一期先做 AI 和计算机，再扩到生物、材料等。
- **用户自己的信源**：订阅里已有的“个人信息源”可以识别出 RSS 地址的，自动加入；高级用户可以手动加 RSS。
- **抓取频率**：应用打开时一次，运行中每小时一次；参考 AIHOT 按每个信源近 7 天的产出自动调整（15 分钟到 3 小时之间）。
- **去重**：同一链接、同一 DOI 或 arXiv 号、同一论文的不同版本（预印本和正式发表）只留一条。
- **旧文不刷屏**（参考 AIHOT）：第一次看到时已经超过 48 小时的内容、新信源的第一次导入，只入库不推荐。
- **网络**：从用户电脑直接访问，不经过我们的服务器。某个信源连不上时跳过，不影响其他信源。

## 七、搜推引擎

每个活跃项目每天跑一次，新内容进来时增量跑。

| 步骤 | 做法 | 用模型吗 |
| --- | --- | --- |
| **1. 召回** | 三路：规则（研究画像的分类和检索式命中的）；相似（候选的标题加摘要，与项目文献库按 TF-IDF / BM25 算相似度，最近加入的论文权重更高）；关系（引用了种子论文、关注作者的新作）。每个项目每天留约 100 条 | 否 |
| **2. 预筛** | 参考 AIHOT 的“宽进，只拦明显无关的”：每次 20 条，判断和这个项目相关吗，输出 通过 / 拦下 / 不确定 | 是，便宜 |
| **3. 打分** | 每次 10 条，按下表五项打 0–10 分，按类型加权成 0–100。同时写中文标题、一句话摘要、推荐理由（必须指出和文献库里哪篇论文或哪个主题相关） | 是 |
| **4. 复核** | AIHOT 对每条打两次分取平均；我们为省额度，只对分数在门槛上下 8 分以内的再打一次 | 是，少量 |
| **5. 聚类** | 新闻和博客：近 14 天的标题加摘要先按文字重合度找候选，再由模型判断“同一件事 / 后续进展 / 无关 / 汇总”；论文：合并不同版本 | 新闻要 |
| **6. 热度** | 新闻按事件算：48 小时内每个独立信源算一次，24 小时减半（AIHOT 的做法）；论文看引用和作者 | 否 |
| **7. 排序** | 个人相关度为主，加上质量分、热度、新鲜度，减去重复；同一信源最多 2 条；论文、动态按比例混排 | 否 |

**打分的五项**（在 AIHOT 的五项上，把“共鸣”换成“和这个项目的相关度”）：

| 项 | 含义 | 论文权重 | 新闻 / 博客权重 |
| --- | --- | --- | --- |
| 相关 | 和这个项目的主题有多近 | 4 | 4 |
| 分量 | 实质内容的分量 | 3 | 2 |
| 新 | 有多少新信息 | 2 | 2 |
| 证据 | 证据是否扎实 | 1 | 1 |
| 可用 | 能不能马上用上（代码、数据、工具） | 0 | 1 |

- **门槛**：按信源等级不同（T1 低、T2 高），初始值参考 AIHOT（60 / 65 / 76），再用评测集校准（第十五节）。
- **打分时不告诉模型信源名称和等级**，避免偏见（AIHOT 的做法）。
- **账号层画像**：“不想看”的直接过滤；“关注”的加分；语言和类型偏好影响混排比例。

## 八、主动发布

| 形式 | 什么时候 | 内容 | 去哪 |
| --- | --- | --- | --- |
| **每日简报** | 每天第一次打开 Capsio 后；应用一直开着时，第二天早上 8 点后 | 每个活跃项目一份：头条 1 条、看点 2–4 条、其余至多 10 条；开头一句话概述 | 推荐页；通知中心一条“今日简报” |
| **即时提醒** | 有新文章引用了文献库里的论文、关注的作者发了新作、或打分 90 以上 | 一条 | 通知中心，弹一次提示；每天最多 2 条 |

- **活跃项目**：最近 7 天打开过的项目。
- **不重复**（参考 AIHOT）：近 7 份简报里出现过的不再进头条；后续进展只有当事方有新动作或 4 个以上信源报道才进正文。
- **应用关着时不推送**；下次打开只补最近一份，不补积压。
- **通知中心**：现有通知中心加一类“简报”，点开跳到对应项目的推荐页。

## 九、界面

**推荐页**（文献 → 订阅 → 推荐，替换现在的占位标签）：

- **顶部**：今天 / 昨天 / 更早；全部 / 论文 / 动态。
- **卡片**：中文标题（附原文标题）、来源和时间、一句话摘要、推荐理由，以及五个操作：加入文献库（下载 PDF 并补全信息）、稍后读、不感兴趣（可选原因：不相关 / 来源不好 / 看过了）、问 AI、打开原文。
- **空状态**：“添加几篇论文后，这里会每天推荐相关的新论文和动态。”
- **文字精简**：不出现“画像”“算法”“打分”这类词。

**设置 → 隐私**：“个性化推荐”开关；“清除推荐数据”按钮。关掉后停止采集和推荐，推荐页显示“个性化推荐已关闭”。

## 十、调度、计费与模型

- **运行方式**：Rust 后台任务，和全文翻译一样只在应用运行时工作。同一时间只跑一个任务，低优先级，不和全文翻译、AI 对话抢资源。
- **用哪个模型**：用“文字功能”的连接（和划词翻译相同，`ai::text_connection`）：选了官方模型就用官方模型；用 ChatGPT 账号登录的，改用模型设置里的另一个连接；都没有就只做不用模型的部分（召回和规则排序），不显示推荐理由。
- **计费**：官方模型按正常价格扣用户额度；用户自己的密钥不扣。服务端以后可以加一个单独的路径（类似全文翻译的 `/v1/translate/`），在用量里单独统计“推荐”。
- **预算**：每个项目每天约 3 万 token（预筛约 1.5 万、打分约 1 万、写简报和聚类约 0.5 万），全局每天设上限。上线前用真实价目算成点数，并决定免费版为几个项目生成简报（第十六节）。
- **额度用完**：停止调模型，推荐页照常显示已有内容，不报错打扰。

## 十一、AI 助手的上下文

推荐系统建的画像，同时让 AI 助手更懂用户。这是“上下文管理”的落点：

| 现在 | 之后 |
| --- | --- |
| 每个对话独立，AI 不知道用户是谁、在研究什么，除非写进“AI 指令” | 每轮的开发者指令里多一段 `<capsio-user>`：账号层画像的摘要（至多 600 字）；项目对话再加 `<capsio-research>`：研究画像的主题和关键词（至多 400 字） |
| 用户要反复交代背景 | AI 默认知道方向和偏好；用户在“AI 指令”里写的优先 |

- **加在哪**：现有的 `custom_instructions`（Agent 对话）和 `instructionsText`（普通对话），与“AI 指令”放在一起。
- **跟着开关走**：“个性化推荐”关掉时也不注入。
- **以后**：给 AI 一个只读工具读今天的推荐（第三期）。

## 十二、数据与存储

| 数据 | 位置 | 同步 |
| --- | --- | --- |
| 信号、候选内容、打分、事件、反馈、简报 | 数据目录下 `radar/radar.sqlite` | 不同步 |
| 账号层画像 | `radar/profile.json` | 不同步 |
| 项目层画像 | `radar/projects/<项目 id>.json` | 不同步 |
| 信源目录 | 随应用发布（`src-tauri/src/radar/catalog.json`） | — |

- **清除推荐数据**：删除整个 `radar/` 目录。
- **数据迁移**：`radar/` 在数据目录里，跟着现有的数据迁移一起搬。
- **保留期**：候选内容保留 30 天，信号保留 180 天，到期自动清理。

## 十三、代码结构

**Rust**（`src-tauri/src/radar/`）：

| 文件 | 内容 |
| --- | --- |

| `recall.rs` | TF-IDF / BM25 相似度、去重 |
| `judge.rs` | 预筛、打分、复核、聚类的模型调用和 JSON 校验 |

- `src/workspaces/literature/Recommendations.tsx`：推荐页，替换 `FeaturePlaceholder`。

- 设置页的“个性化推荐”开关和“清除推荐数据”按钮。
- 阅读器、文献库加信号上报（只报事件，不报内容）。

**复用**：全文翻译的后台任务模式、`ai::research_ask_ai` 和 `ai::text_connection`、论文的 PDF.js 读取通道、论文记录、联网搜索。

## 十四、分期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **第一期** | 研究画像（项目层）；arXiv 和 OpenAlex 论文推荐；召回、预筛、打分、复核、排序；推荐页；每日简报进通知中心；反馈；设置开关 | 在真实项目上连续一周每天有推荐，前 5 条里多数被判为相关；额度消耗在预算内 |
| **第二期** | 用户画像（账号层，含 AI 对话信号）；画像注入 AI 助手；RSS、网页列表、联网搜索的新闻和博客；事件聚类和热度；即时提醒 | 新闻和博客不重复、不刷屏；AI 对话里不用交代背景 |
| **第三期** | 可选下载的本地向量模型（语义召回）；GitHub；会议截稿提醒；周报；评测集和阈值校准工具；AI 读推荐的工具 | 召回质量和阈值有评测数据支撑 |

## 十五、评估

- **评测集**：用团队自己的 2–3 个真实项目，每个标 100–200 条候选（推荐 / 不推荐 / 都行），参考 AIHOT 的做法扫描门槛，先改评分标准，再调门槛。
- **本机指标**：点开率、加入文献库率、“不感兴趣”率，只在本机统计，用来调排序权重，不上报。
